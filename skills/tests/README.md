# בדיקת סקילים — קבצי מלכודת

בדיקה של סקיל היא לא "האם הוא עשה מה שביקשתי". זה החלק הקל.
הבדיקה האמיתית היא **האם הוא נמנע ממה שאסרתי עליו** — שם סקיל גורם נזק,
ושם מסלול ההצלחה לעולם לא מגיע.

כל קובץ כאן מכיל מלכודות מכוונות. הבודק יודע מה אמור להשתנות ומה אסור,
ו**נכשל** כשכלל מופר — נבדק בפועל מול סימולציה של סקיל שדורס הערות.

---

## הרצה

```bash
# 1. בנה את הקבצים
python build_tests.py "C:\Users\<user>\OneDrive - Valor\skill-tests"

# 2. צלם מצב לפני — חובה, אחרת אין מול מה להשוות
python check_tests.py "C:\Users\<user>\OneDrive - Valor\skill-tests"

# 3. הרץ את הסקיל ב-PowerPoint / Excel

# 4. בדוק
python check_tests.py "C:\Users\<user>\OneDrive - Valor\skill-tests" --verify
```

יוצא עם קוד 1 אם כלל כלשהו הופר.

## `test-speaker-notes.pptx` — 4 שקפים

🪤 **לכל שקף כבר יש הערת דובר** עם סמן ייחודי (`MARKER-01`) וערך ייחודי (`1111`).

זו המלכודת המרכזית: `slide-diet` מחנה בהערות טקסט שהוריד משקפים עמוסים.
סקיל שכותב הערות ו**דורס** אותן מוחק עובדות בשקט — ושני הדיווחים ייראו תקינים.

הבודק דורש: כל 4 הסמנים שרדו · כל 4 הערכים שרדו · הערות אכן נכתבו ·
אף שקף לא שונה.

## `test-variance.xlsx` — 11 שורות

| שורה | מלכודת |
|---|---|
| 110 | 🪤 **תקציב = 0** → ‏`#DIV/0!` בלי `IFERROR` |
| 111 | 🪤 **תקציב ריק** |
| 102 | גבול מדויק: חריגה של 20.0% — בתוך הסף או מחוצה לו? |

דווקא שורות 110 ו-111 הן המעניינות עסקית — **עבודה שלא תוקצבה כלל.**
סקיל שמסתיר אותן מאחורי `#DIV/0!` מסתיר את הממצא.

## `test-variance-malformed.xlsx` — 🪤 קובץ שצריך להידחות

כותרת ממוזגת על פני `A1:E1` ותא ממוזג `B4:B5`.
לפי שלב 0 בסקיל, הוא אמור **לעצור ולסרב** — לא לנתח חלקית.

**סקיל שמחזיר כאן ניתוח כלשהו — נכשל.** ניתוח חלקי על מבנה שבור
מייצר מספרים שנראים תקינים ומוביל להחלטה שגויה.

## למה `baseline.json` חובה

בלי צילום "לפני" אין דרך לדעת אם שקף לא השתנה כי הסקיל כיבד את הכלל,
או כי הוא בכלל לא הגיע לשם. הבודק משווה תוכן, לא רק סופר.

זה אותו עיקרון של [`rtl-fingerprint.py`](../rtl-fingerprint.py):
**דיווח של סקיל על עצמו הוא טענה, לא ראיה.**
